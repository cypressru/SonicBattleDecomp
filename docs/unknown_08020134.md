# Random helper translation unit (`0x08020134-0x08020198`)

This complete reconstruction contains three functions, all 100 bytes of their contiguous ROM
extent, and a four-byte private state object. It uses C++ because the original source language is
not established. It does not claim recovered retail names, a surviving object-file boundary, or
original C linkage.

## Boundary and storage evidence

The preceding `FUN_080200f8` initializes unrelated channel/queue state and owns its return and
trailing literal pool through `0x08020134`. The following function at `0x08020198` reads the keypad
and maintains a separate input record at `0x030048E0`. Neither neighbor uses the random state.

The three intervening functions are a seed setter, a linear-congruential update, and a percentage
predicate that performs the same update. Their accepted instruction extents are respectively
`0xA`, `0x10`, and `0x28` bytes. Their complete bodies and pools begin at object offsets `0`, `0x10`,
and `0x2C` and end at `0x64`. All three load the same 32-bit state at `0x0300019C`.

A whole-ROM scan at every halfword alignment finds exactly three words equal to `0x0300019C`:
the literals at `0x08020140`, `0x08020154`, and `0x08020188`. Each is consumed by one of these
functions; no other direct state-address reference was found. This closed state dependency,
contiguous function order, complete literal ownership, and unrelated neighboring modules support
the TU boundary. Indirect or computed addresses cannot be excluded by this scan alone.

The four-byte state is represented with internal linkage. Its location is independently fixed by
all three retail literals, and its width by their word accesses. The source has no initializer;
the seeding function writes the caller-supplied seed. The zero-filled `.bss` target records
storage layout, not bytes recovered from the ROM. This is an evidence-supported reconstruction of
ownership, not a recovered declaration. No remote ROM data is referenced or owned by this unit.

## Language, names, and compiler

All names retain the project's generic address labels. The `u32` type follows word accesses,
unsigned comparison, and modulo-32-bit arithmetic. No metadata or source from another game build
or platform was used to name these helpers. C++ is the requested fallback for unknown language;
the `extern "C"` block preserves the project's synthetic linker names so existing reconstructed
callers can refer to them. It is not evidence of original linkage.

The original C fragments already matched all three instruction extents with pinned agbcc
`-O2 -mthumb-interwork`, but that did not establish language or complete TU ownership.
Unmodified GNU GCC 2.95.2's Thumb C++ frontend/backend with `-O2 -mthumb-interwork
-fno-exceptions -fno-rtti` reproduced the arithmetic, registers, and literals but omitted the
predicate's saved-link-register return sequence. It therefore did not match the whole unit.

`tools/setup_gcc_cpp.sh` builds the GNU GCC 2.95.2 C++ frontend with `thumb.c`, `thumb.h`,
`thumb.md`, and `telf.h` exported from `gcc_arm/config/arm/` at the pinned public agbcc revision
`da598c1d918402c42c0c0d7128ba14567f3175e9`. The GNU archive SHA-256 is
`064e1cb06ea5d2f4a07ec46c1c64d771f74d04f404b6a6766bca2477f7d72482`.
The compatibility patch registers the Thumb ELF target, rejects unsupported profiling, and makes
alignment explicitly zero-filled, as the existing agbcc compiler does when using modern GNU as.
It does not modify instruction selection, optimization passes, register allocation, or emitted
instructions. The C++ flags above then reproduce the complete unit. This establishes a usable
reconstruction toolchain, not the identity of the original compiler.

Integration tests exercise actual C++ preprocessing, overloads, and templates; reject C's implicit
`void *` conversion; and reject sending C++ through the legacy C frontend. Source suffixes select
the actual frontend, not merely an editor language mode.

## Verification

Objdiff verifies all three functions, all 66 instruction bytes, all 34 literal/alignment bytes,
all three `.bss` relocations, and the four-byte `.bss` section at 100%. The full standalone
`.text` is `0x64` bytes. This promotes three already-matching C fragments into one independently
compiled complete C++ TU; it does not add three newly matched functions.

`python tools/check_unit_bytes.py main/unknown_08020134` independently links the compiled object
at `0x08020134`, places `.bss` at `0x0300019C`, resolves every relocation, and compares all
100 `.text` bytes directly with the ROM. No relocated bytes are masked in this comparison.
The target object is sliced independently from the retail ROM rather than composed from the base.

BSBE78 is the repository's only supported ROM target. The full build, repository tests,
proprietary-file check, formatting, payload/debug/function-map checks, normalized objdiff report,
and configured SHA-1 check are required for submission. The existing bootstrap ROM builder copies
the verified base ROM, so its SHA-1 alone is not evidence of source reconstruction. The independent
linked comparison and objdiff establish this TU's byte match. No emulator or physical-hardware
validation is claimed.
